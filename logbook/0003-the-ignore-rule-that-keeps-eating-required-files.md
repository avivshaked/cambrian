# 0003 — The ignore rule that keeps eating required files

**2026-08-02**  ·  Milestone 1

Third time now, so it is a pattern rather than an accident.

`.gitignore` has ignored `*.csproj` since the first commit, for a good reason: Unity
regenerates those files, they contain absolute local paths, and committing them leaks the
developer's directory layout and creates permanent merge noise.

`Evosim.Core` is a hand-written .NET project. Its two `.csproj` files are not generated by
anything, contain no machine-specific paths, and are the only thing that says how the source
compiles. The rule silently swallowed both. A clone would have had twenty-six source files
and no way to build them.

Caught by staging everything and reading `git diff --cached --name-only` before committing,
rather than by anything automatic.

## The pattern

| # | Rule | What it silently dropped |
|---|---|---|
| 1 | `**/manifest.json` (extraction artifacts) | Unity's `Packages/manifest.json` — package restore broken on clone |
| 2 | `spikes/**/results/` | `FINDINGS.md`, which DESIGN.md §11.1 links to |
| 3 | `*.csproj` (Unity generated) | `Evosim.Core.csproj` — nothing compiles on clone |

Every one is the same shape: a rule written correctly for the case in front of it, phrased
broadly enough to catch a category that did not exist yet. They are invisible locally,
because the file is present on the machine that wrote it. The failure only appears in a
fresh clone — which is to say, only to someone else.

The pre-commit guard had the identical hole for the same reason: it blocks `*.csproj`
outright. Exempting `src/*.csproj` there needed a regression check that a Unity-generated
`.csproj` elsewhere is still blocked, because a hook that silently stops blocking is worse
than no hook — [0002](0002-the-spike-that-was-too-fast.md) is the same lesson about
measurements.

## What to actually do about it

Scope ignore rules to the directory whose problem they solve. `research/**/manifest.json`,
not `**/manifest.json`. The narrow rule is one edit away from the broad one and does not
have a category of future files it will silently eat.

And check `git status` after introducing any new *kind* of file — a new project type, a new
tool's config, a new output format. That is when a rule written for the old world quietly
covers the new one.
