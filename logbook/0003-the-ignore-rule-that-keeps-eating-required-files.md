# 0003 — The ignore rule that keeps eating required files

**2026-08-02**  ·  Milestone 1

For the third time, a rule in `.gitignore` written for a good reason has swallowed a file
the project cannot be built without. Three times makes it a pattern rather than an accident,
so this entry is about the shape of the mistake and not about the file.

The rule has ignored `*.csproj` since the first commit. Unity regenerates those project
files, they carry absolute paths from whichever machine wrote them, and committing them
leaks the developer's directory layout and creates merge noise for ever after. All of that
is true and none of it applies here.

`Evosim.Core` is a hand-written .NET project. Its two project files are generated by
nothing, carry no machine-specific paths, and are the only thing that says how the source
compiles. The rule swallowed both of them. A clone of this repository would have arrived
with twenty-six source files and no way to build any of them.

I caught it by staging everything and reading `git diff --cached --name-only` before
committing. Nothing automatic would have caught it.

Here are the three incidents. The middle column is the rule as it was written, and the
right-hand column is what it took with it.

| # | Rule | What it silently dropped |
|---|---|---|
| 1 | `**/manifest.json` (extraction artifacts) | Unity's `Packages/manifest.json` — package restore broken on clone |
| 2 | `spikes/**/results/` | `FINDINGS.md`, which DESIGN.md §11.1 links to |
| 3 | `*.csproj` (Unity generated) | `Evosim.Core.csproj` — nothing compiles on clone |

Each rule was written correctly for the case in front of it, and phrased broadly enough to
catch a category that did not exist yet. All three are invisible on the machine that wrote
them, because there the file is sitting on disk where it always was. The failure shows up
only in a fresh clone, which is to say only to somebody else.

The pre-commit guard had the identical hole for the identical reason: it blocks
`*.csproj` outright. Exempting the two hand-written ones there, which live under
`src/*.csproj`, needed a regression check written first.

That check proves a Unity-generated `.csproj` somewhere else is still blocked. A hook that
silently stops blocking is worse than no hook at all, and
[0002](0002-the-spike-that-was-too-fast.md) is the same lesson about measurements.

So the rule for rules: scope an ignore pattern to the directory whose problem it solves.
Write `research/**/manifest.json` where the broad version said `**/manifest.json`. The
narrow rule is one edit away from the broad one and has no category of future files waiting
to be eaten.

And read `git status` after introducing any new kind of file: a new project type, a new
tool's configuration, a new output format. That is the moment when a rule written for the
old world starts covering the new one.
