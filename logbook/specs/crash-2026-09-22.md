# The blue screen of 2026-09-22, read from its minidump

*Written by the agent on 2026-09-22, the afternoon of the crash, from the kernel minidump
and the Windows Error Reporting queue the owner copied into `scratch/crash/` from an elevated
shell. The reader is `scripts/read-minidump.py`; the dump itself is data and is not committed.*

## What was asked

The machine rebooted without warning at about 13:03 local time, twenty-five seconds after
the GPU probe (`scratch/gpu-spike/probe`, ILGPU on CUDA and ComputeSharp on DirectX 12) had
run. The GPU work was paused until the dump said whether the display driver was involved,
because a probe that can take the machine down is not one to run beside three arms.

## What the dump says

Bugcheck `0x3B`, `SYSTEM_SERVICE_EXCEPTION`: an access violation (`c0000005`) at
`fffff8050f8b0aec`, which is `FLTMGR.SYS+0x10aec`, the file-system filter manager. The
process on the faulting thread was `dotnet.exe`. The return addresses on the saved stack,
innermost first, name three filters and nothing else:

| frame | driver | what it is |
|---|---|---|
| fault | `FLTMGR.SYS+0x10aec` | the filter manager, Microsoft |
| 1 | `FLTMGR.SYS+0x6d9ed` | |
| 2 | `gameflt.sys+0x14e4c` | the Xbox Gaming Services filter (`Gaming Filter`, provider Xbox, altitude 189850) |
| 3–13 | `FLTMGR.SYS`, `ntoskrnl.exe` | the filter chain being walked |
| 14 | `bindflt.sys+0x1f5fb` | the Windows bind filter (WSL, Dev Drive) |
| 15–26 | `FLTMGR.SYS`, `ntoskrnl.exe` | the same chain, one level down |
| 27–37 | `ntoskrnl.exe` | the I/O path |
| 38–50 | `aswVmm.sys` | Avast's virtual-machine monitor, at the bottom of the stack |

`R15` at the fault held `c000009a`, `STATUS_INSUFFICIENT_RESOURCES`. The display driver
`nvlddmkm.sys` (build stamp 2026-01-20) was loaded and appears on no frame; no GPU, DirectX
or CUDA component appears on any.

Two updates were in flight at the time. From 12:30 the AppX deployment service had been
failing every six minutes to delete the previous Gaming Services package
(`Microsoft.GamingServices_38.116.6003.0`, `error 0x5`). The installer transaction for the
new one (`38.117.18001.0`) ran at 13:03:56, fifteen seconds after the boot. Avast's drivers
were replaced at 13:04, also after the boot. The dump's `aswVmm.sys` and `aswMonFlt.sys`
carry a build stamp of 2026-07-14 and `aswSnx.sys` one of 2026-09-02; the files on disk now
are all 2026-09-08 builds (26.9.1026.0). `gameflt.sys`, `FLTMGR.SYS` and `bindflt.sys` are
the same builds before and after.

## The reading

The crash is in the file-system filter stack under a `dotnet.exe` thread doing file I/O,
entered through the Xbox Gaming Services filter while that package was mid-update, with
Avast's older drivers loaded. It is not the display driver, and a user-mode CUDA or
DirectX probe cannot reach the structures the filter manager faulted on. My inference,
marked as such: the Gaming Services update, stuck for half an hour on a file it could not
delete, is the likeliest cause, and Avast's filter the second. The dump cannot separate them
without symbols. Both are outside what this project can change.

What it settles for the project: the GPU spike may resume. The probe's process was the one
on the faulting thread, so the first run after resuming is taken alone, with no arm and no
render beside it, and the machine watched for a minute afterwards.

## The history in the queue

The Windows Error Reporting queue held 49 kernel reports. Six `Kernel_117` display-driver
timeouts, all from 4 to 7 August; one `Kernel_193` the same week; forty-one `1a8` and `1b8`
live-kernel events at boots and resumes from 1 August to 17 September, in pairs; and this one
`3b`, the only blue screen. Nothing from the display driver after 7 August.

## Reading a dump without a debugger

`scripts/read-minidump.py <dump>` parses the triage layout directly. The header at 0
carries the bugcheck and its parameters. The triage block at `0x2000` carries the offsets
of the context, the process and thread blocks, the saved stack, and the driver list with its
string pool. A driver entry is `0x90` bytes: a name offset, three list links, the base at
`+0x38`, the size at `+0x48` and the build stamp at `+0x88`. When the bugcheck is `0x3B` the
fault's own register context is read from the saved stack. The stamps were checked by
reading `ntoskrnl.exe`'s back against the file on disk.
The Windows minidump and the WER queue are readable only from an elevated shell; the owner
copies them into `scratch/crash/` and the agent reads the copies.
