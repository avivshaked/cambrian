# Where the CPU farm's time goes at a full crowd, 2026-09-26 (afternoon).
#
# Why: from round 51 an overnight round runs on the CPU farm with the snow's transport on the card
# (D126), so what is left of a night is the CPU's. Round 49's three seeds (the newest scored, on the
# CPU at 16 threads) are the reference: their rows carry the wall split and, inside the physics, the
# solver's five phases (wallStepGridMs, wallStepWaterMs, wallStepBodiesMs, wallStepCommitMs,
# wallStepAfterMs; DynamicsWorld.PhaseNames).
#
# 1. The wall by phase, from the rows (runs/r49-s{1,2,3}; ms a metabolic step over each third).
#
#   seed  t            alive          total  physics (bodies)  world   pace
#   1     10-10010     22->1542         92      34  (13)         55    5.45x
#   1     10010-20010  1542->3762      134      70  (25)         59    3.72x
#   1     20010-30000  3762->8410      362     259  (94)         84    1.38x
#   2     10-10010     34->4506        195     116  (46)         71    2.56x
#   2     10010-20010  4506->8091      289     196  (76)         77    1.73x

#   the water 26 to 30%, the bodies 36 to 41%, the commit 8 to 12% and the after-step 3 to 7%. The
#   last third of a seed is half its wall or more, and there the physics is three quarters of it.

#
# 2. A sampling profile of the same crowd (scripts/profile-farm.ps1, which runs a resume under .NET's
#    EventPipe sampler and reads it with src/Evosim.Profile). Round 49 seed 2 resumed from 25,000 s
#    for 30 s at 16 threads on scratch/wt-speed's build (round 49 with the serial-phase patch, the
#    solver as main has it), about 8,000 bodies; 41,740 samples pass through an Evosim frame. The 30 s
#    include the restore (World and BedShape construction, about 4%) and the CPU's snow transport
#    (the edge sampling and the passes, about 10%), so the physics' shares below read low by about a
#    sixth. Shares of the Evosim samples:
#
#   inclusive
#     46.6%  DynamicsWorld.StepOne, the bodies' parallel phase
#     25.0%  Water.Sample, the water at every link, velocity and acceleration
#       12.1%  CurrentField.ReefStreamsAccelerationAt
#        9.1%  CurrentField.ReefStreamsAt (the velocity)
#        5.0%  ReefGeometry.Fade, called by both, the same x, y and z
#     17.9%  Contacts.Apply
#       16.2%  Contacts.ApplyPerPart (contact per part, D114)
#       10.4%  ContactGrid.NeighbourLinks (exclusive; the cells a link covers, their buckets, the
#              six range reads per candidate, the sort and the dedup)
#        3.4%  ContactReef.Push, 3.3% of it ReefGeometry.SignedDistance
#      8.9%  Fluid.Apply (exclusive)
#      3.3%  Brain.Step
#      3.0%  Aba.Solve, with Inward, Outward, Seed and SolveSixBySix about 4% exclusive together
#      3.7%  the contact grid's fill (ContactGrid.Fill's two slab lambdas)
#
# 3. What can move with the same bits, and what cannot.
#
#   - The water's velocity cannot be read off the acceleration's gradient. StreamsAccelerationAt
#     evaluates the streams at (2 pi / P) * s and StreamsAt at 2 pi * s / P, which differ by an ulp on
#     half the steps (CLAUDE.md, the water pass), and the velocity is rounded through a float Float3
#     where the gradient keeps doubles. So the separate velocity call stays.
#   - The reef fade is a function of the link's x, y and z alone, and both calls compute it for the
#     same floats: computed once and handed to both, about 2.5% of the Evosim samples.
#   - A candidate's collision test in NeighbourLinks reads six range bounds of the other row, at
#     random. Testing the entry's own cell instead gives the same set after the dedup (a row that
#     covers the queried cell has an entry for it in the same bucket), so the sorted unique list,
#     and every force after it, is unchanged. Its share of the 10.4% is not measured.
#   - The rest is arithmetic whose order the bits fix: the solve, the fluid, the brain.
#
#   Each item is a CPU change checked like the card's: a resume against a round's own rows and
#   checkpoints, and the pace alternated in one sitting. Section 4 is what was built.
#
# 4. Built the same afternoon (branch cpu-physics), and what each did. The paces are round 49 seed 2
#    resumed from 25,000 s for 100 s at 16 threads (9,982 bodies) on round 49's tree with each change
#    applied (scratch/wt-cpu49), alternated; ms a metabolic step from each run's own rows. Every one
#    of the sixteen runs was identical to round 49's own record in 10 samples and the checkpoint at
#    25,100 s. The machine changed speed during the afternoon: the world step, the same code in every
#    build, read 157 to 168 ms in the first eight runs and 100 to 119 in the rest (the fast cores
#    follow the focused window, CLAUDE.md), so a build is compared with its neighbours only.
#
#   build                                  runs   grid   water   bodies   total
#   base (wt-speed)                        1, 4   62.7   103.7   189.9    583
#   the reef fade shared                   2, 5   62.3    87.1   188.9    565
#   + neighbour entries carry their cell   3, 6   69.3    87.4   184.2    567   dropped
#   + a row's bounds in one record         7      63.7    87.4   190.6    569   dropped
#   the fade (faster machine)       12, 14, 16    52.2    71.6   143.2    414
#   + the grid's sort partitioned   11, 13, 15    30.3    71.5   148.5    398
#
#   - The fade shared (CurrentField.VelocityAndAccelerationAt, Water.Sample's one call): the water
#     phase 16% cheaper, about 17 ms a step at this crowd; 16.6 to 15.3 ms at round 50's smoke crowd
#     of 1,700.
#   - The grid's counting sort partitioned by owner (ContactGrid.Fill): each owner used to read every
#     entry twice; now the entries are split among the owners once, stably, and each owner counts and
#     fills its own. The same arrays at any thread count. The grid phase 40% cheaper, about 22 ms a
#     step at this crowd. The bodies phase moved within the machine's noise (normalised by the world
#     step, 1.37 against 1.33).
#   - The two neighbour-query variants bought nothing: carrying each entry's cell made the fill dearer
#     by more than it saved the query, and a row's bounds in one record changed nothing measurable.
#     The query's cost is not the random reads.
#
#   Together about 40 ms off a metabolic step of 400 to 580 ms at 10,000 bodies, 7 to 10%, beside
#   the card's transport (D126). The final build (main-based, both changes) is identical to
#   r50smoke-s1 from 4,000 s for 300 s under the CPU's transport and the card's (30 samples, three
#   checkpoints each), passes Core 995 of 995, Dynamics 118 of 118 (a new test checks every grid query
#   against brute force at 1, 3 and 16 threads, and fails on a planted offset bug) and Farm 192 of
#   192, and the Unity proxy builds. Round 50's own seeds check it again at scale in the morning with
#   the card (logbook/specs/card-transport-check).
